# Role prompts

`src/role-prompts.ts` owns the editable defaults as blocks (`ROLE_BLOCKS`: the shared `contract`, the coordinator's `integrations`, coordinator, worker, scout, reviewer, Host agent; the verifier was retired on 2026-11-03) and `COORDINATOR_CONTEXT_RULES` (the generated context fact and guard), which stays outside overrides. The coordinator's context habits are its editable `context` block. `durable-runtime.ts` assembles the effective text as the sections `prompt-render` shows (host contract: the role line, contract blocks and, for the coordinator, its granted integration blocks; instance and repository instructions; project instructions; role prompt; the preferences brief; skill indexes) and workspace bindings. A task helper has the worker's sections with the return-to-Coordinator delivery. Role prose is edited as prompt blocks (`docs/prompt-blocks.md`, `src/prompt-blocks.ts`); a legacy per-role override still resolves through the same module. Changing prose grants no tools or authority.

Each prompt states the outcome the role owns, not a procedure:

- Coordinator: owns delivery, saves the owner's corrections and lasting preferences to memory without asking (memory grants no execution authority), investigates and makes small changes directly in its persistent chat worktree, and delegates substantial or parallel work with `agents`. Investigations need no Job or PR. It chooses shared or isolated workspaces for task helpers, prepares the environment and integrates their results into its task branch. Its unrestricted shell is trusted local execution; final merge to main, deployment and destructive actions still require explicit owner approval, except `projects_redeploy` where it has it.
- Worker: one block list for both kinds (`ROLE_BLOCKS.worker`). Shared blocks: plan with the `job` tool, prove every criterion with the project's verify skill and `projects_verify_run` up to the round limit, capture proof media, then one full review (one reviewer under 1000 changed lines, the `pr-review` skill at 1000 or more) and up to the project's re-checks (`review.rechecks`, enforced by the `subagent` tool). Only P0 and P1 block Ready. Its required delivery block differs by kind:
  - Independent Job (`delivery-pr`): draft PR at the first push, `job candidate`, `job ready` with unproven criteria as gaps, or `job checkpoint` for questions and unfinished or held work; one short acknowledgment after either. It reports Ready without waiting for CI; Follow PR wakes the Coordinator, which restarts a worker when CI fails. Ending without either report records an automatic checkpoint.
  - Task helper (`delivery-return`): commits, returns its answer with changes, checks, proof, review result, gaps and integration steps, never a PR or Ready. Shared helpers preserve the prepared environment and task branch.
- Scout: read-only investigation with sources.
- Reviewer: reads pinned code and reports findings with evidence; never edits.

After asking the owner for a decision, the Coordinator ends its turn without acknowledgment-only messages to workers. It still processes new results and failures, but reports to the owner only when the result, blocker or decision changes. Compact handbacks point to `agents report` for the full evidence; a short notification is not proof of acceptance.

Independent Job verification and review are worker-owned. The host checks that a Ready report's proof ids are passing runs on the candidate commit. A task helper's `completed` status only means it returned control and an answer. It is not a verification verdict or approval.

Coverage: `durable-runtime-e2e` (quiet-wait and checkpoint instructions in actual model requests), `jobs-e2e` (engine), `repo-skill-overrides-unit` (skill discovery). Instruction checks do not prove that a real model will follow them.
