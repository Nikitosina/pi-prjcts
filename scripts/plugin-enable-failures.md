# Failure modes: per-project plugin enable and disable

Written before the code. Unit: `scripts/plugin-gate-unit.mjs` (the gate in `src/plugin-gate.ts`, no host). E2E: `scripts/plugin-enable-e2e.mjs` (fake model, private HOME, fixture `scripts/fixtures/gated-plugin`; no live host). Owner decision: a plugin that has active work in the project, or that the project's checkout needs, cannot be disabled; nothing is force-stopped and nothing is unloaded globally.

Refusal
1. Disable is accepted while the plugin has a running RPC, tool call or lifecycle task in this project, so the work loses its plugin halfway. The call is refused with a reason naming the plugin and the work; the project record is unchanged.
2. Disable is accepted for a plugin the project's workspace grant needs (provider `github`, or a provider plugin's workspace id). The call is refused with the reason "required by this project's checkout".
3. A call starts in the same tick as the disable: the disable looks at the work count, then the call begins, and a call runs on a disabled plugin. The count check and the stored flag are one synchronous step, and a call after the flag is refused.
4. An unknown or not loaded plugin name is stored. It is refused.

Enforcement for existing threads
5. A thread that already holds the plugin's tools (a frozen worker tool set, a coordinator chat) keeps running them after the disable. Every tool call checks the flag when it executes and fails with "plugin is disabled in this project".
6. A plugin RPC or web route answers for a project that disabled it. Both refuse with the same reason.
7. A background step (Workspace cleanup, Storage usage) of the plugin runs for a disabled project. It is skipped.
8. New workers get the tools of a disabled plugin, or the coordinator prompt names them. Offers and prompt blocks follow the flag.

Isolation and data
9. Disabling in one project disables it in another. The flag is per project.
10. Disabling deletes or rewrites the plugin's stored files for the project. Nothing is touched; enabling again restores the previous behavior.
11. A failed disable (refused) changes the flag, or an enable of an enabled plugin writes again. Both are no-ops.
12. The `plugins` snapshot for a project does not tell the UI which plugins are off or locked, so the toggle cannot explain itself. Each entry has `enabled` and `lock` (a reason or null).

Merge, lifecycle and background work (added in the PR53 repair pass, before the code)
13. A merge call (inspect, markReady, merge, enableAutoMerge, pullMain) of a plugin runs outside the gate: a disable is accepted while an approval merges, and a disabled plugin still merges. Merge providers handed to the approver and to pull-main run each method through the project gate, GitHub's built-in included. Unit: `gate.methods`.
14. The lifecycle pause taken to check a disable is resumed at once, so the plugin restarts its background work in a project that just turned it off. The pause stays held while the plugin is off and is released only by enabling it again. A plugin whose pause refuses blocks the disable and holds nothing.
15. A held pause leaks into another project or survives the enable. It is keyed by project and plugin, and the enable releases it once.
16. A PR monitor or follow tick runs plugin code for a disabled project. The PR and follow providers answer through the gate (a disabled plugin's list and observe never run); the fixture counts calls across a tick interval.
17. Raw VCS access (`findVcsRoot`, `plugins.vcsProviders()`) is path-based, not per project; a project whose folder is a checkout of the plugin's kind cannot disable it (case 2), so a disabled VCS plugin is never one a project's checkout uses. A project with no such checkout never reaches it.
18. A disable whose project save fails leaves the plugin's lifecycle pause held while the plugin is still on (found in the PR53 recheck pass; e2e 14b red before the fix). `setEnabled` takes the save, keeps the pause only after it succeeds and releases it when it throws.
19. After a host restart a disabled plugin's pause is not held (the restart forgets it), so the plugin restarts background work for the project. The host retakes the pause of every project's disabled plugin when plugins finish loading; a refusing plugin stays gated by the flag. e2e 19 (red before the fix).
20. A follow provider's `published` runs for a disabled project, or an `observe` that began before the disable delivers its result after it and the batch records the plugin's items. `published` goes through the gate with the project; `observe` results go through `gate.settled`, which refuses a result that arrives after the flag. Unit: `gate.settled`.
21. The simulator's hourly prune (and one project's cleanup step) removes the test products of a project that turned the plugin off because B stayed on. Ownership is derived: XcodeBuildMCP's workspace key of the project's folder and its git worktrees; only enabled projects' own keys are pruned, unowned workspaces are left. Unit: `workspace-cleanup-unit` T5 with two projects.
22. A failed save of an enable leaves the plugin off with its pause held; the retry enables it and releases the pause once. e2e 14d (added coverage; the path was already correct).
23. A real follow poll runs the plugin's follow provider for a disabled project, or its `published`. e2e 16b with the gated fixture's follow provider: the disabled project's observe and published counters stay at zero; the other project keeps observing. The tick's own per-project interval did not fire again inside the test window, so the check polls by hand through `follow-poll`, the same path.

Third pass (PR 53): entrypoints, fail-closed state and simulator ownership
24. A host-wide plugin RPC without a project id reaches a project through `withRoot` or `mutateIdle` outside the gate: the disable is accepted while that work runs, a disabled project is still reached, and a disable request queues behind the project lock the work holds. Both calls now run through `gate.run` for the named project, counted from before the project is opened or locked, and `project-plugin` refuses on work in flight before it takes the lock. e2e 24 (red before: the disable request waited behind the running work).
25. The gate treated a project whose stored state could not be read as one that has the plugin on. It fails closed: unreadable or missing state counts as off. Unit 25 (red before: the work ran).
26. The simulator took a project's workspaces from `git worktree list`, which names checkouts the host never made, and pruned a checkout two projects claim. Roots are now host-owned (`verifiedWorkspaceRoots`: the folder and the real directories under the project's worker worktree root; links, files and escapes are not claimed). A checkout claimed by more than one project (also one that turned the plugin off) is shared and never pruned; unclaimed workspaces stay. Products of historical worktrees outside the worktree root remain on disk on purpose. `workspace-cleanup-unit` T5-T7.
27. The hourly sweep and the cleanup step deleted without being admitted for the project. Each project's pruning runs through `api.projects.work` (the project's gate: refused when off, counted until the deletion ends). `workspace-cleanup-unit` T8.

Review pass on the isolated candidate (written before the code; e2e 30, 31 and unit 28, 29 were red first)
28. A project that turned a VCS plugin off still gets its worker rule in new worker, scout and reviewer prompts. `plugins.workerRules(project)` skips plugins the project turned off. Unit 28.
29. Changing another provider's workspace grant runs the disabled plugin's `rebind` and rewrites its saved authorization while it is off. The workspace provider's `rebind` is gated by the flag. Unit 29.
30. A Follow PRs poll that another connected provider completes drops the saved state of a provider the project turned off, so enabling it again loses its PR history. Records of a provider the project does not follow now are kept. e2e 30.
31. The open Settings → Plugins list shows a stale switch after the plugin was turned off or on elsewhere. The toggle publishes a `settings` change and an open list redraws when the plugin status changed. e2e 31.
32. A disable is accepted while the plugin reports a write with an unknown outcome (`uncertainWrites`), or when that check cannot be made, so the write is ignored from then on. Owner decision: do not allow it until the outcome is known. The disable is refused with a reason naming the unknown outcome, or the failed or timed-out check (fail closed); the plugin stays on. Work that began during the check refuses the disable too (the gate counts begun calls), so a write started meanwhile is not missed. After a clean disable job admission no longer asks the plugin (a project that turned it off runs none of its code); the other projects' checks and the enable (which asks again) are unchanged. A project disabled before a restart is not asked either. e2e 32 and unit 32 (red before: the disable succeeded and admission asked the disabled plugin).
33. Not enforced: the plugin's prompt block still appears (as off) in the Settings → Prompt editor of a project that turned the plugin off; the owner's saved edits to it stay. Raw VCS executable names (`vcsExecutables`) stay recognized for command profiles; they are classification, not capability.
34. A poll that began while a provider's plugin was off prunes that provider's saved records if the plugin is turned on before the batch is committed or replayed (found in the recheck pass). The batch records `switchedOff` when it is created, and only those providers are kept; a provider that is on but disconnected is pruned as before. Not covered by a test: the window is between the poll start and its commit.
35. The open Plugins list could miss a switch change that arrived during its first read, and a slow read of an earlier project could replace the refresh callback. The callback is installed before the first read and every read goes through one newest-wins path (e2e 31).
36. A Follow poll that began while a provider's plugin was off prunes the provider's saved records when the plugin is turned on before the batch is built. `switchedOff` is read when the poll starts, not when the batch is created. e2e 34 (red before: the record was pruned). Supersedes the "not covered" note of 34.
