# Explicit worker skill access

The owner selected repository skills plus specifically selected configured Pi skills. Access must use explicit project/scope grants, frozen document identities and bounded on-demand reads. It does not grant shell, scripts, MCP, publication or executable approval. Existing projects receive no grant.

## Failure cases recorded before implementation

- Discovery installs/resolves remote packages, starts extensions/MCP, requests a model, changes shared settings or copies credential files.
- A grant accepts an arbitrary caller path instead of a discovered repository/configured skill identity.
- A selected repository skill is exposed to an unrelated repository scope.
- Symlink traversal, nonregular files, invalid UTF-8, oversized documents or changing physical identity evade capture/read limits.
- Referenced documents are read without explicit selection, or a relative path escapes its approved skill directory.
- Skill frontmatter `allowed-tools` becomes execution authority. Bundled scripts are executed rather than read as selected text.
- Skills hidden from automatic model invocation are advertised as automatically applicable.
- Changed grant, selected skill/document, repository authorization or document bytes silently retarget an existing worker binding.
- Missing/disabled access invents results or substitutes a broad filesystem tool.
- Metadata discovery injects all skill bodies or the repository's knowledge tree into prompts.
- Reading exposes a credential/settings/session backing file or a file outside the selected document set.
- Grant changes wait for model/abort/owner shutdown under project locks, or replace a busy/uncertain owner.
- Paging loses Unicode continuation/hash metadata or treats an excerpt as a verified full document.

## Current implementation

`src/worker-skill-types.ts` defines explicit selections and frozen grant/document schemas. Selection inputs contain catalog IDs and relative reference names, not arbitrary roots. A frozen skill has one main document and separately selected references. Repository/configured origins remain distinct. Source metadata records automatic-invocation suppression; it supplies no tool authority.

`src/worker-skill-files.ts` now provides 64 KiB bounded complete UTF-8 capture and frozen-document reads. It checks canonical relative paths, parent/file physical identity, symlinks, backing-file names/private directories and caller-supplied protected backing-file identities. Frozen reads reject changed bytes/physical metadata instead of substituting a newer document. The helpers preserve primary and close failures and execute nothing. `src/worker-skill-backing.ts` supplies the SDK backing-file physical identities used by both owner capture and worker reads, including hard-link checks.

`src/worker-skill-catalog.ts` now captures candidates from selected repository skill directories or caller-supplied trusted public SDK `Skill` metadata. It parses only bounded, pinned text with Pi's public frontmatter parser. Repository candidates must remain under that repository's `.pi/skills` or `.agents/skills` roots without symlinked ancestry. Configured candidates must match the SDK name/description/automatic-invocation metadata; mismatch is a rediscovery blocker. Catalog IDs bind origin, metadata and the captured main document. No body is injected into model context, and `allowed-tools` supplies no execution permission. This helper does not obtain a configured SDK catalog or authenticate caller-provided paths through a public API.

`src/worker-skill-discovery.ts` now scans only a supplied owned repository's `.pi/skills` and `.agents/skills`. It follows Pi's skill-root stopping rule and checks direct Markdown files at each discovery root. Limits are 512 entries, 64 attempted candidates, depth eight and a 1 MiB observed/captured document-size budget. Individual reads still enforce 64 KiB; failed candidates have bounded read attempts too. Symlinked directories/entries and detected directory replacement/change stop discovery. Invalid candidate metadata produces relative-path/fingerprint diagnostics; aggregate read/close failures propagate. Nothing is installed or granted, and skill bodies are not returned by discovery.

`src/worker-skill-configured.ts` captures at most 64 skills from a trusted in-process, already-loaded public SDK `ResourceLoader.getSkills()` snapshot. It detaches the snapshot, bounds diagnostics and accepted-document bytes, verifies SDK metadata against captured text and retains rejection fingerprints. It never calls package resolution, resource reload, extension startup or a model. Missing loaded-catalog access is a blocker. This adapter is not a public API accepting arbitrary skill paths or a replacement SDK resource resolver.

`src/worker-skill-grants.ts` prepares detached grants from captured catalog IDs and current owned workspace scopes. Repository skills cannot cross repository scopes. References require explicit selection, and the total document budget is 1 MiB. Preparation rereads every selected document before returning; it does not persist or enable a grant. Grant revisions bind the selected documents, scopes, owner, enabled flag and workspace authorization. The bounded reader requires a frozen grant ID/revision, rejects inactive/disabled/stale access and rereads current authorization after file IO. It returns at most 4,000 Unicode code points with continuation metadata and the frozen full-file hash. It executes nothing and does not advertise suppressed skills or activate frontmatter tools.

`src/worker-skill-owner-catalog.ts` combines authorized repository discovery with the trusted loaded-SDK adapter. It derives checkout paths from current workspace authorization, rejects provider/identity ambiguity, enforces combined candidate/diagnostic/accepted-byte limits, and rechecks project/workspace identity after asynchronous capture. The detached response has a revision, pinned candidates, rejection fingerprints and explicit unavailable-access blockers. It grants nothing and returns no document bodies. It does not accept caller-supplied roots.

Owner endpoints now expose paged catalog capture, compact paged grant summaries, exact selected-grant reads, confirmed revision-checked grant set, and disabling revocation. Catalog pages default to 16 candidates (maximum 16); the catalog revision binds the full captured catalog. Grant-summary pages default to 16 records (maximum 16); the registry revision binds the full retained registry. `worker-skills-grant-read` retrieves one exact frozen grant record for internal worker-binding integration. Existing projects omit `workerSkillGrants` and therefore have no grants. Repository catalog capture is available through owned workspace authorization. The standalone host deliberately reports the configured catalog unavailable: no arbitrary path or package resolver is accepted. The host supplies protected SDK backing-file physical identities via public `getAgentDir()` and refuses `NODE_OPTIONS` or `PI_PACKAGE_DIR`; absent `models.json` is permitted. Scoped worker bindings in `src/durable-workspace-binding.ts` expose current enabled grants for the assigned scope. `projects_skill_read` accepts only opaque grant, skill and document IDs plus a bounded Unicode range. It checks the active work, project owner, current grant registry and frozen document identity before and after reading. Its metadata-only instruction list omits skills with `disable-model-invocation`; grant changes alter the binding revision and block the old binding. Missing grants add no skill tool or instructions. The host still lacks a trusted loaded configured-skill catalog, so configured skills remain unavailable. Grant changes require an idle owner and close it through the existing lifecycle pattern; persisted grants/documents remain historical after revocation. No grants have been issued.
